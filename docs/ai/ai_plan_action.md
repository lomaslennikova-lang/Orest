# Lesson 12 — план дій: додавання транзакцій за чеком через AI-помічника

**Статус:** етапи 1–2 завершені; очікується commit перед етапом 3.  
**Порядок роботи:** кожен етап завершується перевірками, після чого користувач виконує окремий commit перед початком наступного етапу.

## 1. Мета і межа першої версії

Додати до наявного AI-чату можливість підготувати з чеку у форматі PDF, PNG або JPEG **чернетку однієї чи кількох фінансових транзакцій**, показати її в чаті й виконати створення записів лише після окремого підтвердження користувача.

У першій версії операція обмежена **створенням** транзакцій. Редагування, видалення, автоматичний запис без підтвердження, довільний SQL і прямий доступ LLM до БД не входять до обсягу.

Наявна авторизація вже використовує `require_admin`; право створювати чернетку, підтверджувати й виконувати її матиме тільки автентифікований користувач, чиє ім'я збігається з налаштованим `ADMIN_USERNAME` (поточний Admin). Сервер перевіряє це на кожному endpoint-і — не лише приховує елементи UI.

## 2. Цільова взаємодія компонентів

```text
Користувач
  │ текст + файл чеку; confirm/cancel
  ▼
Frontend AI Chat ── HTTPS/cookie ──► Backend API
  │                                    │
  │ ◄── повідомлення, pending action ──┤
  │                                    ├──► тимчасове сховище вкладення
  │                                    ├──► LLM (тільки текст/зображення чеку та дозволені tools)
  │                                    ├──► БД через server-side service/repository
  │                                    └──► audit-log після успішного confirm
  ▼
Перехід/посилання на «Фінансовий стан» ◄── оновлені дані ── Backend/БД
```

Принципова межа: LLM не отримує `DATABASE_URL`, облікові дані, SQL, сесію БД або інструмент довільного читання/запису. Вона може лише повернути структурований намір/дані для чернетки; backend повторно валідовує їх, зберігає pending action і сам викликає вузький сервіс створення транзакцій після confirm.

## 3. Запропонована модель станів

`uploaded → extracting → needs_clarification | pending_confirmation → confirmed → executed | cancelled | expired | failed`.

- `needs_clarification`: бракує обов'язкових відомостей; запису в БД немає.
- `pending_confirmation`: server-side незмінна чернетка готова для показу.
- `confirmed`: сервер прийняв підтвердження та одноразово запускає виконання.
- `executed`: усі транзакції створені в одній транзакції БД, audit-log записано.
- `cancelled`, `expired`, `failed`: жодної часткової операції не залишається; для `failed` повідомляємо без технічних деталей.

Для ідемпотентності confirm-запит містить `action_id` та ключ ідемпотентності; повторний клік або повторна доставка не створює дублікати. Чернетка прив'язана до `conversation_id`, власника й має погоджений строк дії **15 хвилин**. Додатково, безпосередньо **перед обробкою нового повідомлення користувача в тому самому діалозі** сервер переводить усі його попередні `pending_confirmation`/`needs_clarification` actions у `expired`; ці чернетки більше не можна confirm/cancel. Це відбувається на сервері до виклику LLM і не створює транзакцій або audit-записів виконання.

## 4. Frontend: склад і поведінка AI Chat

1. Додати до composer кнопку «Прикріпити чек» та приховане поле вибору локального файла. Приймати лише `.pdf`, `.png`, `.jpg`, `.jpeg`; показувати ім'я, MIME-тип, розмір, можливість прибрати файл і стан завантаження.
2. Передати текст повідомлення та ідентифікатор успішно завантаженого вкладення до існуючого чату. Файл не інтерпретується клієнтом як достовірні дані.
3. Для `needs_clarification` показати відповідь AI українською із конкретними відсутніми полями; користувач відповідає в тому самому діалозі.
4. Для `pending_confirmation` відрендерити зрозумілу картку «Можливі транзакції»: дата/час, сума, валюта, категорія, тип, продавець або опис (за наявності), джерело «чек». Значення, які не вдалося надійно визначити, не підставляти: картка не має з'являтися, доки потрібне уточнення не отримане.
5. У картці використати наявні стилі й поведінку кнопок проєкту: «Підтвердити» (primary) і «Скасувати» (secondary/danger). Під час запиту блокувати обидві; після результату замінювати на статус, не дозволяючи повторну дію.
6. Після `executed` показати кількість створених записів і посилання «Перейти до фінансового стану». За посиланням відкрити вкладку `Фінансовий стан`, повторно завантажити список/підсумки та, за можливості, застосувати фільтр до створених ID або періоду чеку. Автоматичний перехід не робити, щоб не перервати читання результату.
7. Відобразити обмеження доступу й безпечні повідомлення 401/403/413/415/422/429/503; не показувати стек-трейси, секрети чи сирі відповіді провайдера.

## 5. API-контракт (пропозиція)

| Endpoint | Призначення | Ключовий результат |
| --- | --- | --- |
| `POST /api/ai/attachments` | multipart upload чеку, тільки Admin | `attachment_id`, `filename`, `media_type`, `status` |
| `POST /api/ai/chat` (розширити) | повідомлення + необов'язковий `attachment_id` | звичайне повідомлення або структурований `pending_action` / `clarification` |
| `GET /api/ai/actions/{action_id}` | відновлення стану чернетки під час reload | action, preview, status, expiry |
| `POST /api/ai/actions/{action_id}/confirm` | одноразово підтвердити server-side snapshot | `executed`, `created_transaction_ids`, `finance_url` |
| `POST /api/ai/actions/{action_id}/cancel` | скасувати невиконану чернетку | `cancelled` |

Усі endpoint-и: `require_admin`, перевірка власника conversation/action/attachment, Pydantic-схеми з `extra="forbid"`, обмеження розміру й типу, `Cache-Control: no-store` для відповідей з фінансовими даними. HTTP-семантика: 401 — неавтентифікований; 403 — немає права; 404 — не власний/відсутній ресурс; 409 — action уже оброблено; 410 — строк дії минув; 413 — завеликий файл; 415 — недозволений формат; 422 — неповні або невалідні дані.

## 6. Tools та server-side сервіси

**LLM-facing tools (вузькі й без доступу до БД):**

- `extract_receipt_data(attachment_reference, user_message)` — adapter передає моделі тільки перевірений тимчасовий файл/його дозволене представлення та просить строго JSON: продавець, дата, валюта, позиції/загальна сума, рівень упевненості й перелік відсутніх полів. Для PDF спочатку безпечно отримуємо текст/сторінки; для PNG/JPEG — зображення. Жодної БД.
- `propose_transaction_draft(extracted_receipt, user_context)` — формує лише структуровану кандидат-чернетку або `needs_clarification`. Не має права викликати створення транзакції.

**Backend-only (не реєструються для LLM):**

- `validate_and_create_pending_action` — нормалізує та перевіряє дані, створює незмінний snapshot payload, володіння, TTL і хеш вкладення.
- `confirm_pending_action` — ще раз перевіряє право, статус, TTL, snapshot і бізнес-правила; в одній БД-транзакції викликає існуючу серверну логіку створення транзакції, записує audit-log та переводить action у `executed`.
- `cancel_pending_action` — атомарно переводить тільки власну очікуючу дію в `cancelled`.

План передбачає винесення теперішньої логіки `POST /api/transactions` (`validate_transaction_payload`, пошук/створення Admin і категорії) у спільний сервіс, щоб ручний UI і підтверджена AI-дія застосовували однакові правила: додатна сума, максимум 100 000 грн, дата не в майбутньому, тип `income|expense`, непорожня категорія.

## 7. Контекст і правила для LLM

- Мова діалогу та відповідей — українська.
- Модель не вигадує суму, дату, валюту, тип або категорію. Якщо хоча б одне обов'язкове поле невідоме/нечитабельне/суперечливе, вона просить конкретне уточнення. Категорія є обов'язковою для confirm; нову категорію не створювати без явного підтвердження користувача в чернетці.
- Єдиний дозволений тип у першій версії — `expense`. Дані про `income` у чеку не створюють чернетку транзакції.
- Наявна модель транзакцій використовує UAH. Чек в іншій валюті не конвертувати автоматично: попросити користувача вказати суму в UAH; до цього чернетку не формувати.
- Для чеку з кількома операціями модель явно показує кожну; не об'єднує їх мовчки.
- Промпт трактує текст у чеку та повідомлення користувача як недовірені дані: інструкції на кшталт «ігноруй правила» не змінюють політики.
- LLM не стверджує, що запис створено, доки backend не поверне `executed`.

## 8. Безпека та експлуатаційні межі

- Валідувати MIME за вмістом (magic bytes), не лише за розширенням. Погоджені межі для одного вкладення: до **5 МіБ**; PDF — до **5 сторінок**; PNG/JPEG — до **12 мегапікселів** (і не більше 4 000 px з кожного боку); server-side обробка — до **30 секунд**. Ці межі включають запас щодо двох наданих прикладів: односторінкові PDF 1.7 із вбудованим зображенням, 82 734 та 86 955 байтів.
- Зберігати вкладення поза публічним web-root, з UUID-іменами, без виконання/прев'ю браузером. Строк зберігання чеків — **6 місяців**, керується параметром середовища `AI_RECEIPT_RETENTION_DAYS=180`; cleanup-job видаляє лише прострочені файли та пов'язані з ними технічні метадані. Не надсилати файл до LLM, поки тип і межі не пройдено.
- Не логувати зображення чеку, повний текст, cookie, API-ключі, `DATABASE_URL` чи надлишкові фінансові дані. Додати rate limit окремо для upload, extraction і confirm.
- Виконання доступне тільки з валідної серверної сесії Admin; frontend-стан, `action_id` і payload не вважаються доказом права. Confirm повторно перевіряє статус і власника.
- Audit-log є append-only JSONL-файлом у захищеному runtime-сховищі з контрольованими правами доступу та ротацією. Строк зберігання — **1 місяць**, керується параметром середовища `AI_AUDIT_LOG_RETENTION_DAYS=30`; cleanup-job видаляє або архівує лише прострочені журнальні файли за затвердженою політикою. Один запис створюється **виключно після успішного** confirm: `timestamp_utc` (ISO 8601), `event=ai_action_executed`, `action_id`, `conversation_id`, actor, action type, exact executed payload, IDs створених транзакцій, хеш вкладення. Логи скасування й невдалого confirm до цього файлу не додаються.
- Параметри retention задокументувати в `.env.example` без чутливих значень, валідовувати на старті застосунку як додатні цілі числа та не передавати в LLM/frontend. Pending actions зберігаються лише до старту обробки наступного повідомлення в тому самому діалозі (або до TTL 15 хвилин, якщо нового повідомлення немає). Місце зберігання audit-файлу й політику резервного копіювання обрати з варіантів розділу 14. Файловий audit-log не замінює транзакційність БД; у плані реалізації передбачити обробку помилки запису, щоб не було непомітно виконаної дії без аудиту.

## 9. Сценарії приймання (виконуються й перевіряються окремо)

1. **Успішний чек.** Admin прикріплює валідний чек і просить додати витрату → отримує pending-картку → натискає confirm → сервер створює рівно зазначені транзакції, пише audit-log, UI показує результат і посилання.
2. **Неповні дані.** На чеку немає дати/суми/типу/категорії або вони нечитабельні → AI ставить конкретне питання → pending-картка та запис у БД не створюються, доки користувач не уточнить.
3. **Скасування.** Admin натискає cancel → action має `cancelled`, транзакцій і audit-запису виконання немає, у чаті є повідомлення про скасування.
4. **Повтор confirm.** Подвійний клік, retry або два паралельні запити → створюється один набір транзакцій та один audit-запис; наступна відповідь 409 або відтворює результат ідемпотентно (остаточну семантику погодити).
5. **Не-Admin / чужий ресурс.** Неавторизований або інший користувач намагається завантажити, прочитати, confirm/cancel чужу дію → сервер відмовляє, запису немає.
6. **Недозволений/небезпечний файл.** Невірний MIME, перевищені межі, пошкоджений PDF або image bomb → відмова до LLM, без action і БД-змін.
7. **Збій LLM/мережі/БД.** Користувач отримує безпечне повідомлення; незавершена дія не виконується. Після confirm транзакції та audit записуються узгоджено або позначається потреба безпечного відновлення.
8. **Строк дії.** Confirm після TTL → 410/повідомлення про потребу сформувати нову чернетку; запису немає.
9. **Перегляд результату.** Після успіху перехід до «Фінансового стану» показує нові записи без ручного перезавантаження сторінки.

## 10. Мінімальні автоматичні перевірки після реалізації

- Backend unit: Pydantic-схеми, MIME/signature validation, TTL/state machine, нормалізація payload, відсутність фіктивних значень, правила транзакції.
- Backend integration: upload → pending → confirm/cancel, ролі та ownership, ідемпотентність, атомарність БД+audit, помилки провайдера/БД, cleanup прострочених ресурсів.
- LLM adapter: контракт строго JSON, недовірений текст чеку, неповні/суперечливі чеки ведуть до уточнення, а не до draft.
- Frontend: доступність кнопок/станів, формат картки, блокування подвійного confirm, відновлення action після reload, навігація та оновлення даних.
- Регресія: наявний AI-chat і ручне створення транзакцій продовжують працювати.

## 13. Погоджені рішення та відкриті параметри

1. У першій версії єдиний дозволений тип — `expense` із чеку.
2. Чек в іноземній валюті не обробляється до явного введення користувачем суми в UAH; автоматичної конвертації немає.
3. Категорія є обов'язковою для confirm; нову категорію не створювати без явного підтвердження користувача в чернетці.
4. TTL pending action — **15 хвилин**.
5. Audit-log — JSONL-файл у захищеному runtime-сховищі; один запис створюється виключно після успішного confirm. Записи про cancel/failure не додаються.
6. Межі одного вкладення: до **5 МіБ**; PDF — до **5 сторінок**; PNG/JPEG — до **12 мегапікселів** і максимум 4 000 px з кожного боку; обробка на сервері — до **30 секунд**. Значення обрані за наданими зразками: 1 сторінка й близько 83–87 КіБ, тобто ліміт дає достатній запас для якісного скану чеку без необмеженого навантаження.
7. Строки зберігання конфігуруються через змінні середовища: `AI_RECEIPT_RETENTION_DAYS=180` для чеків і `AI_AUDIT_LOG_RETENTION_DAYS=30` для audit-log. Значення валідовуються на старті; локальні/production-значення не комітяться до Git.

До початку реалізації потрібно обрати місце runtime-сховища й політику резервного копіювання audit-log з розділу 14.

## 14. Варіанти runtime-сховища та резервного копіювання audit-log

| Варіант | Runtime-сховище | Резервне копіювання | Переваги / обмеження |
| --- | --- | --- | --- |
| A — **обрано для поточного Docker-проєкту** | Окремий Docker named volume, змонтований тільки в контейнер `api`, наприклад `/var/lib/orest/audit`; шлях задається `AI_AUDIT_LOG_DIR`. Volume не монтується у frontend або bot. | Щоденний окремий backup-job копіює закриті JSONL-файли у зашифроване backup-сховище; тримати 7 щоденних копій. Перевірка відновлення — щомісяця. | Не потрапляє до Git і не залежить від робочої директорії. Потрібно додати volume та окрему backup-процедуру в Docker deployment. |
| B — локальна розробка | Локальна директорія поза репозиторієм, задана абсолютним `AI_AUDIT_LOG_DIR`; доступ лише користувачу, що запускає API. | Немає автоматичного backup; за потреби ручне копіювання в зашифрований носій. | Найпростіше для development, але не підходить для production і не гарантує відновлення після втрати диска. |
| C — production із керованим сховищем | Локальний runtime-файл у контейнері/volume, як у A; backup-job передає закриті журнальні файли в приватне кероване object storage з шифруванням і обмеженим service account. | Щоденна копія; retention backup-копій 7 днів; lifecycle policy та контроль успішного backup. | Найкраща стійкість для production, але потребує окремого хмарного сховища, секретів доступу й операційного моніторингу. |

Для першого впровадження **обрано варіант A**. З огляду на строк зберігання самого audit-log 30 днів, rotation/cleanup виконується щодня після успішного backup; backup-копії не є джерелом для довшого зберігання й видаляються через 7 днів. Якщо потрібна стійкість до втрати Docker host, перед production слід перейти на варіант C.

## Критерій старту

Реалізація починається лише після Вашого явного повідомлення про погодження цього плану та фіксації відкритих технічних параметрів із розділу 13.
