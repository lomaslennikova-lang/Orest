# AI Actions — підсумок реалізації Lesson 12

**Статус:** реалізовано та перевірено 30 липня 2026 року.

## Створена архітектура

```text
Користувач → React AI Chat → FastAPI (require_admin + ownership)
                              ├─ приватне receipt storage
                              ├─ Gemini receipt-to-draft adapter
                              ├─ pending action state machine
                              ├─ transaction service → PostgreSQL
                              └─ append-only JSONL audit-log
```

1. Frontend завантажує PDF/PNG/JPEG до `POST /api/ai/attachments`; сервер
   перевіряє фактичний тип за signature, межі файла й зберігає його поза
   web-root.
2. Чат передає серверу лише виданий `attachment_id`. Сервер перевіряє власника
   та TTL, читає приватний файл і передає в Gemini тільки файл та повідомлення
   користувача.
3. LLM не має прямого доступу до БД, SQL, `DATABASE_URL`, сесії SQLAlchemy або
   інструментів створення/зміни даних. Її єдиний результат — строго валідований
   JSON `pending_confirmation` або `needs_clarification`.
4. Backend повторно валідовує draft, зберігає immutable `draft_payload` у
   `ai_pending_actions`, а створення транзакцій відбувається лише через
   `POST /api/ai/actions/{action_id}/confirm`.
5. Confirm використовує server-side ownership, TTL, блокування рядка й
   `execution_result` для ідемпотентності. Після успішного виконання створює
   append-only JSONL audit record із UTC-часом, action ID, exact payload, IDs
   транзакцій і хешем вкладення.
6. React показує картку чернетки та кнопки «Підтвердити» / «Скасувати» у чаті;
   після успіху показує посилання на «Фінансовий стан» і оновлює дані.

## Межі й правила

- Доступ доступний тільки авторизованому Admin через `require_admin`.
- Підтримуються лише `expense`; `income` із чеку відхиляється схемою.
- Валюта — UAH. Для чеку в іншій валюті LLM має попросити суму в UAH і не
  виконує автоматичну конвертацію.
- Категорія обов'язкова для confirm; нова категорія створюється лише після
  явного підтвердження картки користувачем.
- Максимуми вкладення: 5 МіБ; PDF — 5 сторінок; PNG/JPEG — 12 Мп і 4 000 px
  на сторону; timeout LLM — 30 секунд.
- Pending action має TTL 15 хвилин і стає `expired` перед обробкою нового
  повідомлення у тому самому діалозі.
- Чеки зберігаються `AI_RECEIPT_RETENTION_DAYS=180`, audit-log —
  `AI_AUDIT_LOG_RETENTION_DAYS=30`; значення конфігуруються через environment.
- Runtime storage у Docker — окремі named volumes, доступні лише `api`;
  audit-log — JSONL у захищеному runtime-сховищі.
- Для чеку з кількома товарними позиціями LLM зобов'язана сформувати окрему
  транзакцію на кожну позицію. За нерозподіленої знижки, комплекту або
  нерозбірливих сум вона має попросити уточнення, а не агрегувати значення.

## Аналіз сценаріїв

| Сценарій | Результат | Підтвердження |
| --- | --- | --- |
| Чернетка з кількома позиціями | У чаті відображено 3 окремі витрати: доставка 109 грн, зоотовари 500 грн та 522 грн. | Ручний скриншот `AI_ACTION_0.PNG` |
| Скасування | Картка попередньої чернетки має статус «Дію скасовано»; транзакції не створюються. | Ручні скриншоти `AI_ACTION_0.PNG`, `AI_ACTION_1.PNG` |
| Confirm | Після confirm UI показує «Дію виконано» і «Створено записів: 3». | Ручний скриншот `AI_ACTION_1.PNG` |
| Перегляд результату | «Фінансовий стан» показує три створені транзакції з датою чеку та сумами 109, 500 і 522 грн. | Ручний скриншот `AI_ACTION_2.PNG` |
| Неповні/небезпечні дані | Строга schema LLM, signature/розмір/сторінки файла та правила draft відхиляють небезпечні або невалідні дані. | Автоматичні тести |
| Повторний confirm | Result зберігається в `execution_result`; повтор не створює нового набору транзакцій. | Реалізація state machine і unit-тести схеми |

## Експлуатаційна примітка

Перед production-розгортанням потрібно налаштувати обраний backup-job для
зашифрованого копіювання закритих JSONL audit-файлів щодня та перевіряти
відновлення щомісяця. Це deployment-операція; вона не виконується LLM і не
зберігає секрети в репозиторії.
