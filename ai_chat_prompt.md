# План інтеграції AI Chat у фінансовий проєкт

> Статус: **планування**. Цей документ не є реалізацією; зміни до коду,
> залежностей і схеми БД мають починатися лише після його погодження.

## 1. Поточна архітектура

Проєкт уже має придатну основу для AI-помічника:

| Шар | Поточний стан | Що можна використати |
| --- | --- | --- |
| Frontend | React 19 + Vite, один екран у `frontend/src/App.jsx`, спільні стилі у `frontend/src/styles.css` | Панелі (`panel`), кнопки, повідомлення `notice`, завантаження через `fetch` з `credentials: "include"`, вкладка «Фінансовий стан» |
| Backend | FastAPI в `app/api.py`, асинхронні SQLAlchemy-сесії | `require_admin`, `AsyncSessionLocal`, Pydantic-моделі, `HTTPException`, CORS |
| Дані | PostgreSQL через `asyncpg`; SQLAlchemy-моделі `User`, `Category`, `Transaction` | Зв'язки транзакцій з користувачем і категорією, суми, тип операції, дата |
| LLM | Gemini REST API у `app/llm.py` | `LLM_API_KEY` у `.env`, класифікований `LLMRequestError`, таймаут та безпечна обробка помилок |
| Поточний AI-виклик | `POST /api/ai/analyze-transactions` агрегує вибрані транзакції і передає Gemini лише підсумки | Принцип «LLM не має прямого доступу до БД», промпт у `app/prompts.py` та `promts/` |

Авторизація зараз призначена для єдиного адміністратора: після `POST /api/login`
backend створює підписану HMAC cookie `orest_admin_session` з `username`, `role=admin`
і терміном дії 8 годин. `require_admin` перевіряє cookie на кожному захищеному
endpoint. Транзакції в БД належать записам `users`, але поточні адміністративні
endpoint-и читають дані всіх користувачів. Отже, на першому етапі чат також є
адміністративним і може аналізувати всі дані; для звичайних користувачів це
правило треба змінити до запуску їхнього доступу.

Найкраще місце для UI — нова панель **«AI-помічник»** на вкладці
«Фінансовий стан», після блоку результату поточного одноразового AI-аналізу і
перед таблицею транзакцій. Це не змішує чат із редагуванням даних і дає змогу
користувачу бачити показники та фільтри поруч.

## 2. Рекомендована схема інтеграції

```text
React AI Chat
  │ POST /api/ai/chat (cookie)
  ▼
FastAPI: require_admin → валідація → перевірка власності діалогу
  │
  ├─► PostgreSQL: діалоги, повідомлення, фінансові агрегати
  │
  ▼
LangGraph (thread_id = conversation_id)
  │ assistant ──► tool node ──► assistant
  ▼                 │
Gemini ◄──── мінімальний результат контрольованого SQL-tool
  │
  ▼
FastAPI зберігає повідомлення і повертає відповідь React
```

LLM отримує тільки системні інструкції, обмежену історію конкретного діалогу,
нове повідомлення та результати tools. Вона **не** отримує облікові дані БД,
`DATABASE_URL`, API-ключі, SQL-текст, ORM-сесію чи необмежений список
транзакцій.

## 3. Frontend: склад і поведінка AI Chat

У `App.jsx` доцільно винести новий компонент `AiChatPanel` (а за потреби —
`AiChatMessage` та `useAiChat`) і використати наявні класи панелей, кнопок та
повідомлень. Нові CSS-правила слід додати локально до стилів адмінки, не
переробляючи загальний дизайн.

Блок міститиме:

- заголовок «AI-помічник»; у першій версії без кнопки «Новий діалог»;
- прокручувану історію з ролями «Ви» / «AI-помічник» і часовою позначкою;
- textarea для запиту та кнопку «Надіслати» (також надсилання `Ctrl/Cmd+Enter`);
- стан «AI-помічник аналізує…» з вимкненими повторним надсиланням і новим
  запитом на час відповіді;
- помилку в стилі `notice` з можливістю повторити останнє повідомлення;
- короткі стартові підказки з підстановкою обраного місяця: «Покажи найбільші
  витрати за `<місяць>`», «Порівняй доходи й витрати за `<місяць>`», «Які
  категорії витрат найбільше вплинули на бюджет у `<місяць>`?», «Чи були
  витрати вищими за доходи у `<місяць>`?» та «Покажи динаміку витрат за
  `<місяць>`». Місяць береться з активних фінансових фільтрів; якщо там не
  вибрано повний місяць, показується селектор від місяця найдавнішої транзакції
  у БД до поточного місяця.

Стан клієнта: `activeConversationId`, `messages`, `draft`, `chatStatus`,
`chatError`. Після завантаження вкладки frontend відновлює останній активний
діалог; після перезавантаження він відновлює `conversation_id` з URL-параметра
або `localStorage`, а сервер завжди повторно перевіряє доступ. `localStorage` є
лише зручним покажчиком, а не джерелом історії чи прав доступу. У першій версії
зберігається і відображається лише останній діалог; список, перейменування,
архівування та перемикання між кількома діалогами не потрібні. Кнопку «Новий
діалог» не показувати; за потреби пізніше її можна додати як «Очистити діалог»
із явним підтвердженням.

На вкладці одночасно виконується лише одна AI-функція. `analysisStatus` і
`chatStatus` мають спільний стан зайнятості: під час одноразового AI-аналізу
поле та кнопка чату неактивні з підказкою «Завершіть поточний AI-аналіз, щоб
почати діалог»; під час відповіді чату аналогічно блокується кнопка
«Аналіз фінансового стану». Після відповіді або помилки обидві функції знову
доступні. Фільтри й перегляд таблиці лишаються доступними, але їхня зміна не
переписує вже отриману відповідь чату.

## 4. Діалоги, історія та БД

### Запропоновані сутності

Під час реалізації додати SQLAlchemy-моделі та міграцію (поточний
`metadata.create_all()` не замінює контрольовані міграції):

```text
ai_conversations
  id UUID PK                 -- одночасно LangGraph thread_id
  owner_user_id FK users.id  -- власник діалогу
  title varchar(160), nullable
  created_at, updated_at timestamptz
  archived_at, nullable

ai_messages
  id bigint PK
  conversation_id UUID FK ai_conversations.id
  role enum/text: user | assistant | tool | system
  content text                -- лише текст, без секретів
  tool_name, nullable
  tool_call_id, nullable
  created_at timestamptz
  status: completed | failed
```

Для поточної ролі admin `owner_user_id` має вказувати на існуючий або створений
системний запис admin у таблиці `users` (так само, як він створюється для
додавання транзакцій). Це забезпечує модель власності вже зараз. Для майбутньої
багатокористувацької авторизації `owner_user_id` повинен походити з
автентифікованої сесії, а не з тіла запиту.

Перед читанням або дописуванням сервер виконує запит на кшталт
`conversation.id == conversation_id AND conversation.owner_user_id == current_user.id`.
Відсутній або чужий ID повертає однаковий `404`, щоб не розкривати існування
чужого діалогу. Історія зберігається в PostgreSQL, а не лише в пам'яті браузера;
отже відновлюється після оновлення сторінки й перезапуску сервера.

Зберігати слід повні повідомлення користувача й остаточні відповіді асистента.
Технічні tool-повідомлення можуть зберігатися в мінімальному JSON для аудиту
або зберігатися окремо з коротким строком життя; їх не треба показувати в UI.
В одному активному діалозі зберігається до 50 останніх повідомлень; старіші
повідомлення та їхній технічний стан видаляються за визначеною політикою.
Відображення також обмежується цими 50 повідомленнями, щоб не перевантажувати
клієнт і контекст моделі.

## 5. API-контракт

Усі endpoint-и нижче потребують `Depends(require_admin)` на першому етапі й
працюють через cookie (`credentials: "include"`).

### Надсилання повідомлення

`POST /api/ai/chat`

```json
{
  "message": "Які найбільші витрати були у червні?",
  "conversation_id": "b5de0f01-0ee2-4d99-9d22-a6618c5590a1"
}
```

`conversation_id` необов'язковий: якщо його немає, backend створює новий
діалог, прив'язаний до поточного користувача. `message` після `strip()` має бути
від 1 до 2 000 символів. Сервер не приймає з клієнта історію, роль, ID власника
або результати tools.

Успішна відповідь `200`:

```json
{
  "conversation_id": "b5de0f01-0ee2-4d99-9d22-a6618c5590a1",
  "message": {
    "id": 42,
    "role": "assistant",
    "content": "У червні найбільші витрати були…",
    "created_at": "2026-07-26T14:05:20Z"
  }
}
```

Помилки: `401` — немає сесії, `404` — діалог не належить користувачу, `422` —
невалідний запит, `429` — перевищено ліміт, `502/503` — LLM недоступна. Текст
помилки для UI має бути без деталей провайдера, SQL або фінансових даних.

### Відновлення історії

- `GET /api/ai/conversations/last` — останній власний діалог (ID, заголовок,
  `updated_at`, короткий preview), або `404`, якщо діалогу ще немає;
- `GET /api/ai/conversations/{conversation_id}/messages?limit=50&before=<id>` —
  пагінована історія власного діалогу;

У першому релізі не потрібні endpoint-и для списку, перейменування, архівації
або явного створення кількох діалогів. Якщо в майбутньому з'явиться така
потреба, їх можна додати без зміни контракту `POST /api/ai/chat`.

Для першого інкременту достатньо `POST /api/ai/chat`, `GET /last` та `GET`
історії останнього діалогу.

## 6. LangGraph, LLM і контрольований доступ до даних

### Граф

Рекомендований граф має стан `messages`, `conversation_id`, `owner_user_id`,
лічильник кроків і технічний статус. `thread_id` LangGraph дорівнює UUID
діалогу. Перевірка власності та завантаження історії виконуються у FastAPI до
входу в граф; LangGraph не ухвалює авторизаційних рішень.

```text
load_context → domain_guard → assistant
                              │
                    є tool call? ── ні ──► persist_response
                              │ так
                              ▼
                         execute_tools ───► assistant
                              │
                      max steps/error ───► safe_failure
```

`domain_guard` реалізується насамперед системним промптом і фінальною
перевіркою відповіді; для дешевого раннього відсіву можна додати детермінований
allow-list намірів. Запит поза темою не викликає tools і отримує стандартну
українську відповідь: «Я допомагаю аналізувати транзакції, доходи, витрати та
категорії цього проєкту. Сформулюйте, будь ласка, запит у цих межах.»

LangGraph checkpointer варто налаштувати на PostgreSQL для стану графа й
незавершених виконань. БД-історія `ai_messages` лишається прикладним журналом
для UI та аудиту. Перед відновленням незавершеного thread сервер повторно
перевіряє власника. Ліміт — наприклад, не більше 4 циклів `LLM → tool → LLM` на
одне повідомлення; при перевищенні створюється безпечна відповідь про те, що
запит потрібно спростити.

### Контекст і промпт

Формувати контекст потрібно на сервері в такому порядку:

1. незмінний системний промпт: українська мова, лише функції фінансового
   проєкту, дані не вигадувати, це інформаційний аналіз, не професійна
   фінансова/інвестиційна/юридична порада;
2. дозволені схеми tools і їхні обмеження;
3. останні повідомлення конкретного діалогу в межах токенного бюджету (не
   більше 50 збережених повідомлень), а для старішої частини — серверний
   стислий summary, якщо його збереження буде погоджено;
4. нове повідомлення користувача;
5. результати tool-викликів лише для поточного запиту.

У разі недостатніх даних модель зобов'язана сказати, чого бракує, а не
заповнювати прогалини фіктивними даними. Дані в запиті користувача є недовіреним текстом: вони не
можуть скасувати системні правила, розширити доступ або підмінити результат
tool. Доцільно обмежити розмір історії, кількість tool calls, розмір результату
tool і загальний таймаут запиту.

### Tools

Усі tools — звичайні серверні функції/сервіси з фіксованими Pydantic-схемами,
а не SQL, який генерує модель. На цьому етапі вони агрегують дані **всіх
користувачів**, бо чат доступний лише адміністратору; вони повертають лише
мінімально потрібні агрегати. Після появи неадміністративних ролей до кожного
запиту обов'язково додається `owner_user_id` з сесії, а не з аргументів LLM.

| Tool | Призначення і параметри | Повертає / джерело | Перевірки |
| --- | --- | --- | --- |
| `get_transactions_summary` | Баланс за період; `date_from?`, `date_to?`, `user?` | Кількість, доходи, витрати, баланс, валюта; `transactions` + `users` | Дати ISO, `from ≤ to`, період не довший за встановлений ліміт, користувач із allow-list |
| `get_category_totals` | Підсумки за категоріями; `date_from?`, `date_to?`, `transaction_type="expense"`, `limit=10` | Масив категорія/сума, кількість; `transactions` + `categories` | `limit` 1–20, лише допустимі типи, мінімальні поля |
| `get_top_expenses` | Найбільші окремі витрати; `date_from?`, `date_to?`, `limit=5` | Дата, категорія, сума; `transactions` + `categories` | `limit` 1–10; без непотрібних внутрішніх ID і персональних даних |
| `get_period_comparison` | Порівняння двох періодів; `current_from`, `current_to`, `previous_from`, `previous_to` | Доходи/витрати/баланс та різниця; `transactions` | Неперетинні валідні періоди, однакова або явно пояснена тривалість |
| `get_daily_expenses` | Динаміка витрат за місяць; `month` (`YYYY-MM`) | День, сума витрат, загальна сума; `transactions` | Коректний місяць, максимум один місяць на виклик |

Опціональний `get_available_periods` може повертати лише мінімальну й максимальну
дату транзакцій, щоб асистент коректно попросив період. Не варто додавати tool
для довільного читання всіх транзакцій: він збільшує витік даних, вартість і
ризик помилкового аналізу.

Виконання tool проходить через реєстр дозволених імен. Аргументи валідовані
Pydantic до SQL-запиту, SQLAlchemy використовує параметризовані вирази, а
результат серіалізується в обмежений JSON. Невалідний аргумент, відсутні дані
або помилка БД повертаються в граф як структурований безпечний результат;
модель пояснює обмеження без технічного стек-трейсу. LLM не повинна мати
інструментів створення, зміни або видалення транзакцій у першій версії.

## 7. Безпека й експлуатаційні межі

- Повторно використати `require_admin`; кожен endpoint діалогів і чат має бути
  захищеним. Власність діалогу перевіряти на сервері для кожного `GET`/`POST`.
- Зберігати `LLM_API_KEY`, `DATABASE_URL`, секрет сесії тільки у `.env`/secret
  storage; не відправляти їх у frontend, промпт або логи.
- Обмежити повідомлення (2 000 символів), довжину історії, tool-відповідь,
  кількість графових кроків, час LLM і частоту запитів за сесією/IP. Додати
  rate limit для `POST /api/ai/chat`.
- Логувати request ID, `conversation_id`, тривалість, код результату, назву
  tool і лічильники; не логувати текст повідомлень, суми, категорії, cookie або
  ключі. Для діагностики — редаговані/хешовані значення.
- Усі відповіді мають явно відокремлювати аналіз даних від професійної поради.
  Prompt injection, позатематичні запити й вимоги розкрити дані/системний
  промпт відхиляються однаково.
- Визначити строк зберігання історії, спосіб архівації та право на видалення
  до production-запуску. Використати HTTPS і `Secure` cookie поза localhost.

## 8. Послідовність реалізації після погодження

| Етап | Мета, файли та залежності | Критерій готовності / головний ризик |

## 9. Мінімальний набір тестів

1. Перше повідомлення без `conversation_id` створює діалог і повертає його ID.
2. Друге повідомлення з тим самим ID отримує попередній контекст і продовжує
   тему, а після оновлення сторінки історія завантажується з API.
3. Запит про підсумки/найбільші витрати викликає коректний tool, передає LLM
   лише агрегат і повертає відповідь українською.
4. Запит поза тематикою не викликає tool та містить зрозуміле пояснення меж.
5. За порожніх даних асистент повідомляє про недостатність даних, не вигадує
   суми й не падає.
6. Невалідні дати, ліміти та типи в tool-викликах відхиляються без SQL-помилок.
7. Таймаут/помилка Gemini, невалідна tool-відповідь і помилка БД дають безпечний
   HTTP-статус, повідомлення UI та не створюють помилкову відповідь assistant.
8. Неавторизований запит отримує `401`; чужий `conversation_id` — `404`; у
   multi-user тесті жоден користувач не читає історію чи дані іншого.
9. Ліміти: довге повідомлення, часті запити, завелика історія та більше ніж
   дозволено tool-циклів контрольовано обмежуються.
10. Перевірка логів/відповідей гарантує відсутність cookie, API-ключів,
    `DATABASE_URL`, SQL і надлишкових фінансових записів.

## 10. Питання для погодження

1. Погоджено: у першій версії чат доступний тільки поточному `admin` та
   аналізує агреговані дані всіх користувачів. Розширення React-авторизації і
   персонального доступу — окреме майбутнє завдання. Поле `owner_user_id`
   лишається в моделі діалогу як основа для такого розвитку.
2. Погоджено: користувачу доступний лише останній діалог (до 50 повідомлень),
   який зберігається на екрані та відновлюється після перезавантаження. Список,
   перейменування й архівація не входять до першого релізу.
3. Погоджено: використовуємо LangGraph і PostgreSQL checkpointer для стану
   діалогу та відновлення незавершених виконань.
4. Погоджено: фінансові дані не мають штучного обмеження за часовим періодом.
   Обмеження частоти — не більше 10 AI-запитів за хвилину для admin; це саме
   кількість звернень до API, а не кількість повідомлень у діалозі.

## Резюме

Пропонується вбудувати AI Chat у вкладку «Фінансовий стан», зберігати діалоги й
повідомлення у PostgreSQL, ідентифікувати LangGraph thread через UUID діалогу
та викликати Gemini лише з серверного графа. Дані до моделі потраплятимуть
винятково через валідувані read-only tools з мінімальними агрегатами. Такий
підхід продовжує чинну Gemini-інтеграцію, зберігає поточну адмін-авторизацію та
створює безпечну основу для майбутньої багатокористувацької моделі.
